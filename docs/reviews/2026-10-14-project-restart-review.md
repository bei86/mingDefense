# 游戏项目设计审核与重启建议

审核日期：2026-10-14  
审核基线：`master` / `c2cb544`  
用户确认的方向：尽量还原原作规则和数值。

## 1. 结论与现状

项目值得继续，原有的布阵、合成、随机招募、自动战斗、局内成长核心循环，以及先第 1 关、再第 1 至 5 关、最后扩展的交付方式合理。模拟与表现分离、配置驱动、固定时间步长、本地先行也值得保留。

但是，两份文档目前属于“总体方案加不完整参考资料”，还不是可直接执行的还原规格。应先明确原作证据、消除 M1 范围冲突，再实现首关。不能以完成 50 关或者接入账号作为重启后的第一目标。

本次检查确认：

- 当前仓库只有两份已跟踪设计文档，没有应用代码、项目依赖、素材、构建脚本或可运行游戏。
- 本地可见分支只有 `master`，六次提交均为文档提交，最近一次为 2026-08-11。
- 审核前工作区干净。上述现状只涵盖当前仓库及本地可见历史，不代表其他目录或远程一定没有项目文件。
- 本次读取两份完整设计、核对提交历史和三篇引用攻略，并复算时长、经济和排期；没有游戏可供运行、试玩或性能验证。

## 2. 按优先级排列的问题

### A1：还原目标与原创规则混在一起，必须先拆清

证据：总体设计第 7 行要求玩法高度一致，第 151–188 行自行规定跨关恢复、Buff 选择和重试，第 174–180、208–220 行设计原创 Boss 与成长曲线。

当前参考资料支持招募、合成、击杀经验、强化、180 秒限制和每五关 Boss 等大方向，但没有证明这些具体 Boss 技能、恢复规则、免费重试制度和成长公式就是原作规则。公开攻略中的“卡退回溯”也不能直接当作正式失败重试机制。

建议：建立逐项规则台账，分别标记“实机确认”“攻略记载”“推断”“项目改动”。核心玩法以还原为准；原创角色、美术和命名可以保留，原创 Boss 行为、经济和成长规则要单独列出，避免被默认为原作事实。先确定要还原哪一次活动/版本，不能把不同版本攻略拼成一个版本。

### A2：M1 的范围存在直接冲突

证据：总体设计第 107 行只开放 1 至 3 阶；英雄设计第 130 行要求验证六阶属性、三阶与五阶技能，并在开工前补齐三个英雄的六阶生命值。

这会把本应快速完成的首关闭环，变成等待 18 个生命值和五阶技能的任务。现有生命表只有招财桃 1 阶的 240，三个 M1 英雄生命值全部缺失。

建议：统一 M1 为三个英雄、1 至 3 阶，最少先确认 9 个生命值及相应技能参数；4 至 6 阶另设内容验收阶段。若坚持 M1 就包含六阶，则需明确增加资料和实现工作量，不能沿用原首关排期。生命值只是缺项之一，攻速、射程等也必须补齐。

### A3：商店经济和棋盘扩容缺少决定性规则

证据：总体设计第 111–115 行没有初始资源、展示数量和购买价格，第 233 行规定购买与刷新均耗果；第 112 行默认购买进入待部署区；第 226 行才提到解锁容量或备战位。

实时核对的攻略只明确“15 果刷新”和招募，没有证明招募还要另付购买费用。攻略还明确区分有无备战席，并描述刷不到格子导致无法摆放。这意味着初始格子、格子来源、备战席开放时点可能是核心策略，而非普通 UI 配置。

建议：先确认刷新后的单位如何取得、是否额外付费、是否能跳过、满场如何处理、格子如何解锁、备战席是否默认存在、出售/丢弃规则。不能用通用自走棋的商店行为补空白，否则经济与合成难度会偏离原作。

### A4：空间、移动和仇恨规则不足，站位玩法尚未定义完整

证据：总体设计第 100–106 行只定义占格数量与合法放置，第 121、458 行只概括移动和索敌；英雄设计第 68 行给出同阶仇恨顺序，但未明确距离、阶级和路径的优先关系。

缺少棋盘尺寸及初始可用格、2/3/4 格具体形状、旋转许可、出生位置、我方是否移动、敌方如何绕行、攻击距离、阻挡和换目标规则。原攻略强调前排低阶单位引怪来回移动，这些规则会直接决定站位是否有用。

建议：用一段清晰实机过程和示意图定义第一关的空间规则，至少记录一次敌人选目标、移动、目标重伤后重新索敌的过程。将同距离/同优先级的平局处理也写明，方便复现。

### A5：技能数值存在重复倍率与不可靠来源风险

证据：英雄设计第 26–29 行承认部分数值是等效攻击值；第 27 行说天蓬猪表值已经计入 120%，第 101 行再次描述 120% 倍率。若实现时再乘一次，就会重复加成。齐天猴五、六阶表中的 `×2` 同样需要与第 97 行双段技能区分。

实时核对昆多攻略发现：招财桃第二项写成 `0.556 个/秒`，与相邻数值和作者的低阶经济论述不协调，存在明显疑似笔误。文档使用 18 秒/个属于合理校正候选，但本次没有实机证明。御剑鹰五阶原文仍存在破损文本，不能把还原出的 480 标成实机确认。

建议：配置分别记录基础攻击、普攻倍率、攻击段数、触发周期和附加技能，另保留参考面板值与来源。原文笔误、推导值、测量值必须区分，避免把“看起来合理”当作准确。确认天蓬猪第三次攻击是替代普攻还是附加攻击、范围是否包含主目标；确认御剑鹰残留剑阵的触发、叠加和命中时刻。

### A6：战斗升级、波次结束、重试与检查点边界不完整

证据：总体设计第 26 行描述击杀升级选择强化，第 90 行战斗只允许有限操作，第 151 行则把 Buff 选择放在关后；第 96 行首关有三个波次，第 123 行又用“敌人全部消灭”作为胜利条件。

需要确认升级发生时立即暂停选择还是关后选择，以及连续升级是否排队。多波次情况下，场上敌人暂时为零不一定代表本关完成。检查点也没有写清位于发奖励、选 Buff、刷新和开战的哪个时点，可能影响重试资源与重复领奖。

建议：明确状态转换表和奖励只结算一次的边界；胜利应包含本关无待生成波次/召唤且没有存活敌人等条件。退出当前战斗、失败重试和刷新恢复分别定义，不能笼统共用“重试”。

### B1：确定性架构正确，验收条件还需收紧

证据：总体设计第 130 行要求同种子同结果，第 115、320、334 行分别描述多种随机行为、仅商店随机状态和操作日志。

同种子但玩家购买、位置、Buff 选择不同，结果本来就应该不同。准确条件应是相同规则/内容版本、初始状态、种子和输入序列下结果一致。共享随机流时，新增一个随机调用也可能改变后续商店或 Buff 序列。

建议：记录必要的随机状态或定义可重建方式，隔离商店、Buff、战斗随机流；稳定实体迭代与同帧结算顺序。1 倍与 2 倍以相同逻辑时刻的操作比较。最初验证范围先限定相同运行环境，跨浏览器或跨语言一致性另验收。保留首关重演能力，暂不实现在线成绩验证系统。

### B2：时长与排期偏乐观，不能直接当作重启承诺

证据：总体设计第 53、139–145、443 行。

- 五关战斗目标合计 345–450 秒，即 5 分 45 秒至 7 分 30 秒，尚未计入购物、布阵、Buff 和重试。若“5 至 8 分钟”指完整循环，当前预算基本没有整备时间。
- 引用的九游 50 关攻略估计一局约 100 分钟，与设计的 1 倍速 50–80 分钟不同；两者均不是本项目已测结果。
- 原排期 M0–M7 合计 61–104 个工作日，按每周五个工作日约 12–21 周，还未计大批量正式美术、资料补齐和额外返工，与总述“10–16 周”不完全一致。

建议：把战斗时间、玩家整备时间和完整局时长分开记录；本轮仅评估“规则补齐后到首关可玩”的计划。原 M0+M1 的 8–12 个工作日可作内部粗估，不能覆盖尚无时限的资料采集；五关以后根据实测再估。

### B3：长局需要中断恢复，但内容扩展顺序应后移

证据：总体设计第 54 行长局耗时较久，第 326–329 行已有本地保存设计，第 77–78 行先做 50 关再补完整内容。

本地整备检查点合理，应在五关连续循环阶段验收；云存档可后做。先铺到 50 关，再验证英雄、控制和流派，容易把缺少机制差异的重复内容扩展得太早。

建议：首关验证闭环，五关验证成长与 Boss，再用约十关验证代表性的经济、控制、辅助和输出组合，确认能形成不同策略后再扩展 50 关。正式美术、账号、排行榜继续后移。

### B4：招财桃经济说明合理，但完整平衡尚无依据

两只 1 阶每分钟合计产 6 果，一只 2 阶每分钟约产 3.33 果，合成后总产出下降约 44.4%，英雄文档第 74–78 行的计算正确；用产出换棋盘空间是可解释的取舍。

但招财桃 4 升 5 阶的产出变化很大，若同时高生命、强仇恨且可大量铺场，强弱还取决于初始格子、价格、存活时间、敌人路径和技能。没有这些数据不能判断是否失衡，也不应仅因面板不平滑就改掉待还原数值。

英雄文档第 79 行的“两只 2 阶招财桃”具体推荐，本次读取三篇引用正文未找到对应表述；第 68 行完整仇恨顺序也没有在三篇正文找到，应补充独立出处或实机证据。这是证据缺项，不足以证明规则错误。

## 3. 值得保留的设计

| 内容 | 审核判断 |
| --- | --- |
| 手机竖屏 H5，桌面居中预览 | 平台边界明确，适合先验证触控玩法 |
| 第 1 关、五关循环、再扩展 | 保留，以可玩验收而非文档数量推动进度 |
| 原创命名和素材 | 可以与玩法还原同时推进，占位素材不影响规则确认 |
| TypeScript + Vite，Phaser 战场与 React 界面 | 对当前 2D 玩法的职责划分合理，首期控制集成复杂度 |
| 会话命令层统一修改规则状态 | 可避免 UI 与战斗模拟各维护一份不一致状态 |
| 纯规则模拟、固定时间步长、表现独立 | 有利于倍速、批量验证和后续重演 |
| 配置校验、本地检查点、版本信息 | 保留，先实现首关必要部分 |
| 单机后在线 | 保留，后端不应成为第一关的前置依赖 |

技术栈判断为对设计适配性的评估，本次没有进行依赖安装、版本兼容或实机性能验证。

## 4. 重启路线选择

| 路线 | 得失 | 建议 |
| --- | --- | --- |
| 先还原一个可验证首关，再扩展 | 资料范围小，能尽快暴露规则误解；不能宣称完整还原 | 推荐，符合本次目标 |

## 5. 第一批应该交付什么

### 第一步：原作基线和资料缺项清单

产出一份“首关还原规则表”，每项包含字段、值、单位、适用版本、来源链接/截图/录像时间点、可信度、是否阻塞 M1。未知字段保持未知。

| 必须核对的组别 | 最小内容 |
| --- | --- |
| 棋盘 | 行列、初始可用格、扩容方式、英雄具体形状、是否旋转 |
| 招募 | 初始果子、刷新费、展示数量、领取/购买方式、初始概率、满场处理 |
| 合成 | 条件、操作方式、目标位置、占格变化、是否支持连续合成 |
| 三个首期英雄 | 1–3 阶生命与基础攻击、攻速、射程、三阶技能参数 |
| 基础敌人和第一关 | 生命、攻击、速度、攻击间隔、出生与波次、奖励、经验 |
| 战斗空间 | 双方移动、距离判定、仇恨、阻挡、换目标 |
| 流程 | 升级选 Buff 时点、重伤恢复、退出/失败后的处理 |

不必先把八英雄 48 个生命字段全部填满。若选定三个英雄不符合原作首关可获得的内容，应按实机首关调整样本，并记录原因。

资料不足时，仍可实现与未知数值无关的 H5 容器、生命周期、规则配置校验、随机数工具和棋盘占用算法；测试夹具值必须标为测试用途，不能进入还原内容配置。

### 第二步：统一首关实施规格

解决 A1–A6，确定 M1 的三个英雄、阶级范围、棋盘、招募、波次和战斗参数。把原作规则与项目有意改动列在同一张差异表中，便于审核。规则未确认前不自行填默认生命值，也不为主观平衡调整原作数据。

### 第三步：搭建框架并完成首关闭环

建议按以下顺序，每一步形成可运行结果：

1. 竖屏容器、启动、资源占位、页面后台暂停。
2. 棋盘及配置校验、单位摆放和合法性反馈。
3. 原作确认的招募、资源处理、待部署/备战逻辑、同名同阶合成。
4. 纯规则战斗、基础敌人、首关波次、胜负与一次性结算。
5. 1 倍/2 倍速、固定种子重演、触控主流程、失败/退出处理。

第一批验收：手机能完整经历招募、布阵、至少一次合成、自动战斗和胜败结算；非法操作不污染状态；没有提前结束波次；相同初始状态及输入下倍速结果一致；后台返回没有时间跳跃；连续 20 局没有状态残留或重复结算；代表性实机样本能按同规则解释。与原作的差异需有记录，不能只以“能赢”作为还原验收。

### 第四步：五关闭环再做长期内容

首关通过后，加入原作确认的成长/Buff、第一个 Boss、跨关恢复和本地检查点。再加入经济、控制、护盾等代表性英雄，验证站位与构筑取舍，之后扩展关卡和六阶内容。账号、云档、排行榜和防作弊保持在后续在线阶段。

## 6. 现在最具体的下一件事

制作首关规则/数值台账，统一“仅 1–3 阶的 M1”还是“六阶 M1”，并补齐首关阻塞资料。随后按闭环批次实施。

目前不能承诺忠实首关的开工完成日期：缺少实机基线和关键参数。但可以立即推进已知规则及不依赖数值的框架工作，不需要等 50 关全部资料。
